# bac-v15：BSK 强身份初始化与兼容边界优化计划

## 通俗解释：究竟发生了什么

- **一句话说明：** BSK 已经能发放新式防伪票，但售票口仍默认出售没有姓名和班次的旧票；这张票能进第一站，却无法通过后面的严格闸机。
- **具体场景：** v15 调用 `state transition` 时没有传 run，BSK 接受请求并写入 `attempt_id=default` 的 literature State。后续 Gate 带上新身份后，Kernel 又正确拒绝转移，于是形成“入口放行、出口永久锁死”。
- **对应到本问题：** v2 State identity 是新式票，legacy event 是旧票，Skill runtime 声明是该线路的售票规则，State invariant 是后续闸机。
- **改变前后：** 当前调用者必须知道哪些额外参数才会真正启用 v2；改进后，声明要求强身份的 Skill 无法创建 legacy State，错误在首条事件写入前发生。

## 专业判断：问题在哪里

- BSK 2.1.1 已实现 `state_visit_identity`、`atomic_target_identity_handoff`、`attempt_supersede`、State-bound Gate 和 action authorization，bac-v14 所规划的核心身份模型已经落地。
- `state transition` 的 `--run-id` 仍是可选项，`--attempt-id` 仍默认 `default`；只有已有 v2 快照或显式提供 target attempt/visit 时才进入 v2 分支。因此新运行仍可无提示地产生 legacy State。
- 当前 CLI 把“读取旧日志”和“继续创建旧协议事件”混为同一兼容策略。旧日志可读是必要兼容，新任务静默降级不是必要兼容。
- Skill runtime 声明已经提供 State、required Verifier 和版本信息，但没有让 Skill 声明“本运行必须使用 v2 identity”的统一政策字段；Kernel 无法按调用者契约收紧参数。
- BSK 已有运行快照能力，但普通 State 初始化没有强制绑定实际 Skill 版本、State/Verifier 契约哈希和 Kernel 环境，事后难以证明究竟执行了哪个安装副本。
- v15 还暴露出控制边界：Kernel 能阻止非法 transition，却不能让外部业务动作自动受控。已有 action authorization 应形成更清晰、易消费的标准模式，但不能把领域调度写进 Kernel。

## 要达到什么目标

- 允许旧事件确定性读取和重放，同时阻止声明为强身份的 Skill 在新任务中继续写 legacy State。
- 提供领域无关的原子初始化能力：建立 workspace、运行快照和首个 v2 State visit/attempt，不产生身份空窗。
- CLI、Python API 和 capability 输出对身份模式使用同一语义；调用者无需通过隐含参数组合猜测是否进入 v2。
- 新 State、Verifier、Gate、action authorization 和 completion consumer 能绑定同一 run/visit/attempt 及运行契约快照。
- 保持 BSK 领域中立，不出现 literature、candidate、research-idea 等业务语义。

不在本次范围内：实现某个 Skill 的科研判断、阻止任意外部文件写入、自动修改系统安装副本，或把旧事件无证据升级成 v2/completed。

## 改进方向

### 分离“旧日志可读”与“新事件可写”

在 runtime 声明中增加领域无关的 identity policy，例如要求 `state-identity-v2`。加载带该政策的 `--skill-root` 时，初始 transition 必须具有非空 run 和目标 attempt；Kernel 生成或验证 target visit。缺失字段、`default` attempt 或显式 legacy 降级均在事件追加前返回稳定错误码。

未声明强身份的旧 Skill 可暂时保持原行为，但 CLI 应明确返回 `identity_mode=legacy` 和迁移警告。已经进入 v2 的任务继续禁止降级。

### 提供原子 State 初始化入口

增加通用的 State 初始化操作，或扩展 workspace init，使调用者一次提交 Skill runtime、run 和 initial attempt。Kernel 在同一事务边界内完成声明解析、运行快照、初始 State helper、首个 visit 创建、事件追加和 meta-state 提交；任何失败都不得留下半初始化任务。

该入口只处理通用身份与持久化，领域 manifest 仍由 Skill 管理。Skill 可在调用前准备参数，或在初始化成功后写入自己的业务材料，但不能绕过身份创建。

### 让 v2 模式显式而可检查

CLI 输出和 `bsk capabilities` 增加当前请求实际选择的 identity mode、必需字段和 downgrade policy。不要再让“是否提供 target attempt”成为唯一隐式开关。Python API 使用结构化 `source_identity`、`target_identity`，对空字符串、`default`、跨 run 和已 supersede attempt 统一早拒绝。

### 绑定实际运行契约快照

原子初始化记录 Skill ID/version、State 与 Verifier 版本、关键声明/契约哈希、Kernel 版本和最小化解释器指纹。后续 verifier、gate、action 和 transition 引用该 snapshot ID；若执行中的 Skill 根或契约哈希变化，要求显式开始新 run/visit/attempt，而不是继续复用旧 Gate。

快照不得保存完整 prompt、本机绝对路径或凭据；路径只保留脱敏来源类型和内容哈希。

### 收敛 State-bound action 的标准使用方式

明确 action authorization 是外部业务动作的通用 preflight/consume 协议：授权必须绑定 active visit/attempt、action ID、请求哈希和有限有效期；attempt supersede 或 State transition 后自动失效。提供精简的 Python/CLI 调用结果，便于 Skill 适配器把它放在业务调度前。

Kernel 不负责调用具体业务工具，也不宣称能拦截绕过协议的任意进程；它只保证官方调用者获得的授权不可跨身份复用。

### 改善环境与失败诊断

提供机器可读的运行环境诊断，至少包括 CLI 使用的 Python、Kernel 包版本、协议和 capability；下游可与当前 `sys.executable` 加载结果比较。身份缺失、解释器错配、legacy snapshot、契约漂移和 invariant 失败使用不同 reason code。

## 实施范围与顺序

1. 先冻结 strict identity policy、原子初始化输入输出、运行快照绑定和 legacy 读写边界；复用 bac-v15 现场作为不可接受的新写入样例。
2. 在 State transition/reducer/快照事务中实现严格初始化，确保 policy 生效时不存在 v1 写入分支。
3. 将 verifier、Gate、action authorization、attempt supersede 和 transition 统一绑定运行 snapshot 与 active identity。
4. 补 capability、环境诊断、legacy 警告、稳定错误码和迁移说明；保持未声明 strict policy 的旧调用者兼容。
5. 发布前用通用 fixture 和至少两个不同 Skill 适配样例验证，不在 Kernel 测试中硬编码领域判断。

## 如何确认完成

- 声明 strict identity 的 Skill 在省略 `run_id`、省略 initial attempt、使用 `default` attempt 或请求 legacy 模式时，首条 State 事件写入前失败。
- 同一 Skill 使用原子初始化后，一次得到 workspace、运行快照、初始 State、run、visit 和 active attempt；事件重放与 meta-state 完全一致。
- 任一步发生异常时，恢复后不存在“workspace 已就绪但首个 State 身份残缺”或“State 已写入但运行快照缺失”的分裂状态。
- legacy v1 日志仍可读取、status 和 rebuild；它不能通过 strict Skill 的后续操作被自动升级，也不能获得新的完成资格。
- v2 任务中跨 run、错 visit、旧 attempt、旧 Gate、旧 authorization、契约哈希变化和并发重复都返回稳定原因码并 fail-closed。
- `bsk capabilities` 与环境诊断准确报告实际解释器、Kernel 版本、协议能力和 identity policy；下游能确定性识别双 Python 环境。
- State-bound action 在正确 identity 下可 preflight/consume，State 转移或 attempt supersede 后立即失效；绕过协议的边界在文档中明确。
- 包内 pytest、CLI smoke、实时/重放一致性、并发与故障注入、legacy fixture、package-data、构建检查和 BAC verify 全部通过。

## 技术补充（按需阅读）

- 建议把 strict policy 视为 Skill runtime 契约，而不是全局删除 legacy：这样能保持旧调用者可读可运行，同时确保已经声明新协议的 Skill 不会静默降级。
- 原子初始化的核心不变量是：首个 State 事件、meta-state、run snapshot 和 target identity 要么全部提交，要么全部不可见。
- 对 strict 模式，`attempt_id=default` 应视为无身份，而不是普通字符串；可读 label 与权威 ID 如需并存，应由 Kernel 分字段表示。
- Kernel 包版本仍由项目负责人决定；本计划只建议该变更属于协议/CLI 行为变化，需要按仓库规则评估 major 或 minor 版本及迁移说明。

## 风险与待确认事项

- 全局把 `--run-id` 改为必填可能破坏旧调用者；优先采用声明驱动 strict policy，并用 deprecation 周期逐步收紧默认值。
- 原子 workspace + State 初始化不能吞并 Skill 领域 manifest，否则会破坏 Kernel 与领域适配器的职责边界。
- 运行快照绑定会增加事件体积，应只记录版本、哈希和最小诊断，不复制契约正文。
- action authorization 只能约束采用它的调用路径；文档必须避免把它描述为操作系统级沙箱。
