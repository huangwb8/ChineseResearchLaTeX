# nsfc-justification-writer 论证修订优化计划

本计划基于当前 Skill 及其配置、参考资料和脚本编写，供维护者审阅。本轮仅新增计划和项目记录；以下行为均为拟实施内容。

## 通俗解释：这次要改善什么

一份申请书即使语言流畅，也可能没有交代清楚“现有研究为什么不足以回答这个问题”。另一方面，已经论证合理的稿件，也可能在润色时被改得面目全非。本次优化要让 Skill 更准确地判断哪里值得改、应该改到什么程度，以及哪些地方需要作者作出科学判断。

例如，原文说“已有研究未考察跨平台表现”，修订时应保留这一证据边界，并说明它与项目问题的关系。如果改成“现有方法无法跨平台泛化”，就把“没有研究”变成了“做不到”。优化后，Skill 应识别这种含义变化，完成有依据的语言修改，并把需要更多证据的判断单独列出。

## 专业判断：现有能力与主要缺口

当前 Skill 已覆盖科学问题导向、研究路线综合、可证伪预测、自然叙事、正文与审查记录分离，以及路径、引用、结构命令、备份和回滚检查。此次适合在现有流程内补强修订判断。

从现行规则中可以确认以下不足；它们代表规则尚不充分，不等于已通过实际样稿证明每次都会发生相应错误。

| 现状 | 可能影响 |
| --- | --- |
| 结构判断、规划、生成与审查集中完成，缺少明确的修改幅度依据 | 润色成熟稿件时，可能按默认结构过度重写 |
| 研究局限的分类与公允比较要求不够明确 | 将证据空缺写成方法缺陷，为项目制造过大的创新空间 |
| 小结明确安排前期工作，假设段的证据承接要求较弱 | 先提出假设，之后才补上支持它的观察 |
| 材料不足时允许缩小主张并继续，缺少科学含义变化的处置细则 | 保守改写也可能改变作者原有的因果主张或研究方向 |
| 部分段数、限定数量和章节表述偏硬 | 为满足形式规则删掉必要条件，或调整原本合理的结构 |
| 审查信息丰富，但修改总结与作者决策事项尚未清晰组织 | 作者难以快速看出改动理由，以及需要自己决定的内容 |

## 要达到的目标与范围

完成后，Skill 应先识别任务属于新写、重构、审查还是润色，再根据实际问题决定修改范围。每项重要调整有可解释的依据；研究现状、前期证据和假设之间形成清晰联系；科学主张变化透明可见。

保留现有分工：宿主 AI 负责语义判断，Python 负责确定性检查和安全写入。继续保留自动写入、写前备份、白名单、只读预览和回滚行为；保留当前章节职责、无默认目标字数和广泛学科适用性。

本次不扩展研究内容或技术路线写作，不引入自动文献综述、固定生物医学身份、词语黑名单、机械语义评分或额外运行基础设施。计划不包含 Verifier、State、Pack 接入；本轮未调用 verifier-state-architect。

## 改进方向

### 一、先诊断，再选择最小有效修订

在现有流程开头增加简短诊断，明确全文科学主张、论证主线及影响论证的关键障碍。将发现分为“必须修复”“建议优化”“可以保留”，每项重要问题注明位置、依据和影响。

- **新写**：从材料建立论证，缺失信息显式登记。
- **重构**：允许重排和合并段落，但解释调整如何改善论证。
- **审查**：交付诊断与建议，不调用会写入正文的默认 preview。
- **润色**：优先局部修复，保留合理结构和作者声音；发现实质问题时单列说明。

这些属于任务语义，不新增 CLI 子命令，也不恢复已经移除的旧 review/coach 接口。诊断可以在一次执行中完成，不增加逐阶段确认。

用户应能看出“为什么改”，合理原稿也可以得到“建议保留”的结论。

### 二、公允分析研究现状，准确界定缺口

在综合研究路线时，先说明已解决的问题及贡献，再讨论与本项目直接相关的限制。明确区分：

1. 已有工作已考察但尚未解决的问题；
2. 现有材料中尚未研究或缺少评价的问题；
3. 在明确假设或理论条件下不能解决的问题。

“未找到相关报道”不能直接升级为“首次”“空白”；对现状全面性的判断应受已读取文献范围约束。材料不足时说明待核验内容，避免把局部材料当作完整领域证据。

同时区分性能提升与科学贡献。方法学项目可以围绕可识别性、收敛性质、误差界、表征规律和泛化条件提出科学问题，无需强行改写为生物机制。

用户获得的研究必要性应建立在准确比较之上，而非贬低前人工作。

### 三、按论证作用安排前期证据

将前期材料分为三种用途：支持假设的观察、支持实施可行性的基础，以及仍待验证的探索性线索。

参与假设推导的关键观察，在提出假设之前或紧邻假设交代；小结只回收要点。实施基础简要衔接到研究基础章节，避免展开技术细节。外部研究与申请人前期结果分别标明来源，避免把文献发现写成团队成果。

没有前期结果时，允许依据已有文献提出有边界的假设，登记支持不足之处；不强制添加“前期基础”段落或虚构结果。论证链表示内容之间的关系，不要求新增固定标题。

用户应能理解假设从何而来，并区分“支持这一想法”与“能够实施项目”的证据。

### 四、对科学含义变化实行透明处置

建立三类修订边界，统一用于诊断、正文生成和最终审查。

| 变更性质 | 默认处置 |
| --- | --- |
| 压缩长句、澄清指代、合并重复且不改变主张 | 直接修订 |
| 调整句段顺序、改善证据衔接且不改变科学关系 | 修订，在总结中说明重要调整 |
| 改变因果方向、机制解释、研究对象、适用范围或核心假设 | 未获相关授权时仅给建议，不自动替换正文主张 |

“证明”降为“提示”、“导致”改为“相关”同样需要核对证据。依据明确、符合既有修订授权的纠错可执行并说明；材料不足以判断时，标明不确定性，不以保守措辞掩盖决策。

默认自动流程继续完成可保真修订。若待决主张使相关段落无法形成可信成稿，保留该段原文、指出未解决问题，交付其余可用修订和可选建议，不宣称全文已可直接使用。生成候选解释不等于作者确认采用；已有明确授权无需再次询问。

用户无需为普通措辞逐项确认，同时能掌握项目科学含义的实质变化。

### 五、统一软预算与科学完整性的优先级

明确段数、比例和主题组织属于默认建议。将“每段最多一个核心限定”调整为“合并重复限定，保留所有会改变科学解释的必要条件”。多项必要限定可通过拆句、重排或分段提高可读性。

已有结构能完成研究意义、现状、问题、假设和承接功能时，保留合理标题及 LaTeX 命令；不为匹配默认内容链而改动章节结构。结构命令变更仍执行现有授权和脚本检查。

同步 SKILL、质量控制、README 和配置注释中可能产生硬上限误解的表述。优先保持现有字段兼容，不新增预算配置或更改解析语义。

用户的必要证据、限定和引用应优先于形式上的整齐。

### 六、提供清晰的修订总结与证据说明

保留完整正文提案及现有 diff、备份和回滚信息，面向作者的说明统一组织为四类：

- **论证结构改进**：重要调整及其理由，可明确说明结构已合理、予以保留。
- **学术表达改进**：概括关键变化，不逐句罗列普通措辞。
- **科学歧义与证据缺口**：位置、当前依据、不确定性及需要补充的资料。
- **作者决策事项**：具体选项、对论证的影响及当前采用状态。

已有证据等级、外推边界和保留限定等记录归入相应类别，避免再复制一套重复报告。简单润色可以简短交付，无问题类别写明“未发现”即可。

引用复核区分 bibkey 存在、文献信息可核验、文献支持具体主张三个层次。句段移动后检查引用与主张是否仍匹配；未读到足够文献内容时，不能宣称已完成支持性核验。数学表达、标签、数值和引用的保留继续列入语义复核，不把编译成功等同于科学保真。

## 实施范围与顺序

| 顺序 | 工作与交付 |
| --- | --- |
| 1. 复核事实与规范 | 执行前重新读取目标 Skill、真实脚本接口和上游现行规范，核实测试入口；确认修改仅涉及当前能力。 |
| 2. 统一修订原则 | 优先落实诊断分级、缺口分类和科学主张变更边界，再补前期证据位置与软预算规则。主流程简洁，细则放参考资料。 |
| 3. 同步用户入口 | 更新四类交付说明、README 和必要配置注释，补充针对性案例；版本仅在 config.yaml 更新，变更记录区分计划与已实现行为。 |
| 4. 定向验收 | 用下列案例核对保真、论证和任务范围，检查文档、引用与可用脚本接口，记录结果和未验证项后交付。 |

主要影响 `SKILL.md`、`references/section_writing.md`、`references/quality_control.md`、`references/regression_examples.md`、`README.md`、`config.yaml` 和 Skill 及仓库 CHANGELOG。Python 默认保持现有实现；只有验收发现与本次目标直接相关的确定性缺口，才评估最小脚本修正。

## 如何确认完成

### 语义验收案例

沿用现有回归样例，补充以下关键场景。以科学含义、证据关系和修改理由评阅，不以固定措辞或改动比例评分。

| 场景 | 验收结果 |
| --- | --- |
| 成熟稿件请求润色，原有标题不符合默认四节形式 | 保留合理结构，修改有依据，不为套模板重写 |
| 原文仅说明跨平台表现尚未评价 | 不推导为方法无法泛化；缺口表述匹配证据 |
| 前期观察支持假设，但原文只在末尾提及 | 将关键证据前置或紧邻假设，来源和证据强度不变 |
| 因果表述依据不足，作者未授权改变核心主张 | 完成其余保真修订，待决主张及候选修改透明可见 |
| 一个判断同时依赖两个必要条件 | 两个条件均保留，正文仍然通顺 |
| 计算或理论课题研究可识别性、误差界 | 科学问题准确，不被强行改写成生物机制或性能口号 |
| 调整句段顺序，引用、公式、标签与数值随文保留 | 引用仍支持对应主张，受保护内容无无依据变化 |
| 用户仅要求审查 | 仅交付诊断与建议，无正文写入 |

至少对成熟稿润色、材料不足的因果主张和方法学课题进行旧版与修订版同输入对照。保存正文与审查说明，人工判断改进是否成立；这属于实施阶段验收，本轮尚未执行。

### 确定性检查与完成标准

- 核对受影响文档、配置注释和交叉引用一致，版本唯一来源仍为 config.yaml。
- 使用真实可用的配置校验和文档检查入口；安全写入相关验证使用隔离样稿及任务目录，不修改真实申请书。
- 当前文档列出的 `tests/test_semantic_boundaries.py` 未在本轮文件清单中找到。执行时先定位现行测试；若确实缺失，纠正失效说明，并按实际风险补足必要验证，不直接宣称历史测试通过。
- 语义案例均有输出及判断依据；未解决的科学问题明示，审查任务不写入正文。
- 无无关重构；项目与 Skill 变更记录、BAC 记录及验证摘要与实际修改一致。

## 风险与审阅重点

本方案最需要审阅的是科学主张处置边界：建议保留自动完成能力，仅将未经授权且依据不足的实质变更留作建议。这样可能交付带有待决段落的修订稿，但能避免把不确定判断包装成完整定稿。

诊断分级也可能增加报告负担，因此只要求解释重要问题，简单任务保持简短。软化结构预算后，仍用论证功能、必要限定和专业可读性约束质量，避免放任重复或松散叙述。

本轮只确认计划及其事实依据；Skill 行为是否改善，须在实施后通过上述案例验收。
