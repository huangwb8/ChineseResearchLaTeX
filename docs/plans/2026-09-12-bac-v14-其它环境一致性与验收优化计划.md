# bac-v14：其它环境一致性、诊断与验收优化计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 当前“依赖检查通过”只确认工具材料在柜子里，却没有确认真正执行任务的人拿到的是正确版本，因此错误环境也会显示 PASS。
- **具体场景：** v14 机器上的 `bsk` 来自 Python 3.12、Kernel 2.1.0，而默认 `python3` 是 Python 3.9、加载 Kernel 0.11.0；现有 `check_dependencies.py` 只查找依赖 Skill 目录，仍返回通过。
- **对应到本问题：** 依赖检查是开工前体检，定向测试是交付验收，报告校验与完成检查分别代表“格式可读”和“流程完成”；这些信号必须各自准确，不能互相冒充。
- **改变前后：** 当前用户可能在启动后才遇到身份协议错误；改进后启动前就能看到实际 Python、Kernel、BSK 路径、版本和能力是否匹配，并获得明确的修复建议。

## 专业判断：问题在哪里

- `config.yaml` 声明 Python 3.11+ 和 Kernel `>=1.0.3`，但 `check_dependencies.py` 只检查 required Skill 是否可发现，不检查 Python、Kernel、`bsk` 或同环境一致性。
- 单纯判断 `>=1.0.3` 不足以证明兼容。v14 在 Kernel 2.1.0 暴露了旧测试未覆盖的更严格 State identity 行为；“版本更高”不等于“集成已验证”。
- 当前定向测试 28 passed、3 failed，失败项恰好是端到端阶段入口、全阶段推进和可迁移副本；不能用其余通过数掩盖核心路径失败。
- `validate_report.py` 对 v14 返回 PASS 仅说明报告结构合格，并同时给出 `completion_eligible=false`；`check_completion.py` 返回 FAIL 才是控制链没有完成的结论。两个信号需要在用户界面和文档中明确区分。
- v14 已证明证据哈希、报告诚实降级和完成检查的安全价值；本计划不重复 bac-v13 中已落实或已通过核验的内容质量改造。

## 要达到什么目标

- 启动前准确验证实际解释器、Kernel 包、BSK CLI、依赖 Skill 和所需协议能力。
- 测试结果能代表正式文档所描述的五阶段运行，而不是只覆盖局部 API 或使用失真的 fixture。
- 对用户统一输出“环境可运行、报告结构合格、控制链完整、科学证据充分”四类互不替代的状态。
- 安装副本、项目源码和测试环境之间的版本漂移可被发现，但不记录本机隐私路径。

不在本次范围内：自动升级系统包、修改用户全局 Python、放宽科研证据门槛，或把安装器功能塞进 `research-idea`。

## 改进方向

### 方向一：把依赖检查升级为运行环境预检

`check_dependencies.py` 除 Skill 发现外，还应检查 Python 最低版本、当前解释器加载的 Kernel 版本与位置、`bsk` 实际入口所属解释器，以及配置声明的最低版本。路径只在终端诊断中显示，写入日志/BAC 时使用脱敏后的环境标识。

对普通用户的变化：开工前即可发现“命令行 bsk 和 python 不是同一套环境”。

### 方向二：从版本判断升级为 capability 判断

在 BSK 提供协议能力查询后，预检要求 State visit/attempt、required Gate、绑定 handoff 和目标身份交接等实际能力。尚无 capability API 时，以最小临时 workspace 做无业务数据的 smoke probe；探测失败必须 FAIL，不能因版本号较高继续。

对普通用户的变化：系统检查“会不会做这件事”，而不只是“包装盒上的版本号够不够大”。

### 方向三：建立真实的兼容与集成测试矩阵

保留局部单元测试，同时新增按正式运行指南执行的五阶段 CLI 测试。测试初始化必须使用真实身份；每阶段使用文档规定的新 attempt，并覆盖失败重试、回退、续跑和完成收敛。最低支持 Kernel 与当前生产 Kernel 都要跑，未验证的新版本只能标为 unknown/unsupported，不自动推断兼容。

### 方向四：统一诊断结果和退出语义

提供一个聚合诊断入口，分别报告 environment、report schema、control completion 和 evidence/claim eligibility。任何 FAIL 都附稳定原因码、当前 State、检测到的版本/能力和恢复动作；`validate_report PASS` 不得在摘要中缩写成“任务通过”。

### 方向五：检查安装副本与源码漂移

运行项目内 Skill 时记录版本、关键契约哈希和实际加载根；若同时发现安装副本，提示是否一致，但不自动覆盖。发布或安装验证应证明安装后的脚本、State、Verifier 和配置与发布源一致。

## 实施范围与顺序

1. 先扩展环境预检与结构化原因码，立即消除 Kernel 0.11.0 仍返回 PASS 的误报。
2. 接入 BSK capability/协议检查；在新身份 API 未发布前将完整控制链标为 unsupported，而不是继续运行。
3. 修正失真的测试 fixture，建立最低版本与生产版本的五阶段矩阵，并把核心路径失败设为阻断项。
4. 统一诊断摘要、README、运行指南和 CI/发布检查；旧环境只提供明确迁移提示，不自动修改。

## 如何确认完成

- 默认 Python 3.9 / Kernel 0.11.0 与 Python 3.12 / BSK 2.1.0 混用的 v14 环境被预检准确拒绝，并指出解释器不一致和版本不足。
- 缺 required Skill、找错安装副本、Kernel 版本不足、能力缺失和 CLI/模块不一致均有独立测试及稳定原因码。
- 正式五阶段集成测试在受支持矩阵全部通过；若核心路径失败，即使大量单元测试通过，整体验收仍失败。
- 同一份阶段性报告可同时得到“schema PASS、control FAIL、claim ineligible”，摘要不会将其误写为 completed。
- 诊断日志和 BAC 不包含用户目录、解释器绝对路径、凭据或完整 handoff；安装副本漂移检查可复现。
- research-idea、依赖检查、安装/发现、文档链接、`git diff --check` 与 BAC verify 通过。

## 风险与待确认事项

- capability probe 若创建临时 workspace，必须位于任务目录并自动避免业务文件；不得修改真实运行事件。
- 兼容矩阵会增加 CI 成本，应以最低支持版和当前生产版为核心，不无限覆盖所有历史版本。
- 环境检查只诊断和给出建议；安装、升级或切换解释器仍需用户明确授权。
