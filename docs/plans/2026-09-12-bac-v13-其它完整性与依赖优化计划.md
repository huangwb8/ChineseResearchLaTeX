# bac-v13：其它完整性、依赖与审计问题优化计划

## 通俗解释：究竟发生了什么

- **一句话说明：** 即使把状态闸门补上，查新资料、审查独立性和完成检查仍可能只留下“看起来齐全”的文件，而没有足够证据证明内容真的完成。
- **具体场景：** v12 在所有候选、查新、review 和报告都生成后，才在不到一秒内集中写入 Verifier/Gate/State；同时查新依赖还出现过 `primary_source=null` 崩溃，synthetic review 也缺少真实独立执行元数据。
- **对应到本问题：** 这些是 BSK 和主编排之外的质量与可追溯性问题，涉及下游 Skill、`check_completion.py`、parallel review、报告契约、工作区和 BAC 说明。
- **改变前后：** 现在文件存在可能被误读为工作完成；改进后系统分别报告“产物存在、执行可追溯、证据充分、结论可交付”，缺一项就降级。

## 专业判断：问题在哪里

- `check_completion.py` 主要检查最终报告和终态，不能验证完整中间路径、Gate 早于产物，或来源内容是否在 Gate 后发生变化。
- Premium 查新缺少稳定来源 ID、全文/摘要深度、强近邻清单、等价性检查和依赖失败的统一降级规则；临时 workaround 不能证明查新完成。
- synthetic review 有多份结果文件，但缺少 thread、模型、输入快照、上下文隔离、启动/结束时间和输出哈希，不能强证明独立性。
- 论文解读、研究 map、最终报告对“原文证据”和“综合推断”的区分不足；BAC 的本地完整性也不能外推为现实贡献真实性。

## 要达到什么目标

- 完成检查能够识别越级、事后回填、错绑定、证据变化和依赖失败，并给出可恢复原因。
- 查新、论文解读和 review 产物具备稳定来源、读取范围、内容哈希、失败原因和执行元数据。
- 报告区分 `artifact_ready`、`execution_recorded`、`evidence_sufficient`、`claim_eligible`；`recommended`、`insufficient`、`degraded`、`completed` 的含义不再混淆。
- 工作区、BAC 和文档能指出当前权威 attempt、历史结果是否被替代以及 BAC 无法证明的边界。

不在本次范围内：重构 BAC 核心账本、构造真实科研 ground truth 数据集、替用户提交论文，或修改系统级 Skill 安装副本。

## 改进方向

### 方向一：增强完成收敛和时序检查

扩展 `check_completion.py` 及其测试，校验完整 State 路径、每次 Gate/Verifier 绑定、事件与产物的时间顺序、manifest/source 哈希、attempt 关系和报告声明。报告生成前后的状态矛盾、Gate 后证据变化和事后批量回填必须失败。

对普通用户的变化：文件齐全不再自动等于流程完成，系统会指出缺的是执行证据还是内容证据。

### 方向二：修复查新和文献证据契约

修复 `primary_source=null` 等 runner 崩溃；为每条候选记录 DOI/稳定 ID、来源 URL、检索时间、全文/摘要/网页状态、PDF 获取结果、覆盖范围和失败原因。Premium 只在最低证据深度和强近邻等价性检查满足时作为推荐依据，否则标记 `degraded` 或 `insufficient`。

对普通用户的变化：查新结论能回到具体论文和读取范围，而不是只回到候选数量。

### 方向三：让 synthetic review 可审计

为每个 reviewer/轮次记录真实 thread ID、模型、输入快照哈希、是否看到上一轮结果、启动/结束时间、输出哈希和失败状态；汇总必须引用全部原始结果。只有角色化草稿而无执行元数据时，明确标为 `synthetic_review`，不能计入 required independent review。

对普通用户的变化：多份意见是否真的独立，有可检查的执行证据。

### 方向四：统一报告和工作区的证据分层

统一论文解读和 research map 的 `source_id`、`evidence_depth`、`read_scope`、方法、结果、限制、支持/反驳和引用字段。报告 frontmatter 明确四维完成状态、降级原因、当前 attempt 和恢复位置；续跑自动更新 README，历史 attempt 标记 `supersedes`。

对普通用户的变化：能清楚区分原文事实、AI 综合判断和仍待人工确认的内容。

### 方向五：明确 BAC 与依赖故障的可信边界

依赖失败必须保留失败证据并停止或降级，不以静默 workaround 覆盖。报告说明 BAC 只能证明本地账本结构和记录链的状态，不能证明作者身份、现实贡献或没有遗漏。

## 实施范围与顺序

1. 先建立 v11/v12/v13 脱敏 fixture 和四维完成模型，确保后续修复有反向回归基线。
2. 修复完成检查、来源绑定和事后回填拒绝；让其消费 BSK 提供的事件/授权证据。
3. 修复 literature-search、Premium 查新和 interpretation 的字段、失败和证据深度契约。
4. 增强 parallel review 执行元数据和独立性判定，再同步报告模板、README、运行指南和 CHANGELOG。
5. 最后补 BAC/依赖边界说明，并进行人工抽查：从报告反向定位到来源、review、Gate 和事件。

## 如何确认完成

- v12 事后回填样本不能通过；合法样本的每个产物均能定位到当前 attempt 和较早的 Gate。
- `primary_source=null`、全文不可得、网络不可观测和强近邻未核验均有明确失败/降级结果，不写成无条件 complete。
- review 测试能验证轮次、人数、输入隔离、输出哈希和汇总覆盖；缺真实执行元数据自动降级。
- 报告中的四维状态、outcome、当前 attempt、降级原因与 meta-state/events 一致；历史报告保留且不可冒充当前权威结果。
- `python -m pytest -q tests/research-idea`、相关下游 Skill 测试、JSON/YAML/文档校验、`git diff --check` 和 BAC inspect/verify 通过。

## 技术补充（按需阅读）

- 内容哈希必须由宿主按规范化字节重算；文件大小和修改时间只能作为辅助线索，不能替代哈希。
- `uncertain`/`unchecked` 不得被转换为 `pass`；无法观测来源时应转人工复核或阶段性结果。
- 新结论应创建新 attempt，不能修改旧事件或用新来源覆盖旧报告；投稿前查新必须重新运行。

## 风险与待确认事项

- 多源全文和真实独立 review 会增加网络、时间和 token 成本，需要允许透明降级而不是放宽门禁。
- ground truth、审计记录和 reviewer 元数据可能包含隐私，应最小化、脱敏并排除 BAC。
- 旧任务缺少新字段时只能只读兼容；不能凭旧字段追认新的完成等级。
